# How it works

## How Pumpkin gets the permissions

Pumpkin keeps a list of permission values per player and reads wildcards from the broadest one. It also reads a permission set exactly as a wildcard for everything below it. PumboPerms on Pumpkin and PumboBridge behind PumboProx send each player a list that Pumpkin reads the way PumboPerms decides:

- Every permission of the Pumbo plugins gets its own value (`pumbobans:ban`, `pumbofilter:bypass` and so on), even when your data only has a wildcard such as `pumbo.*`.
- A wildcard with a narrower wildcard of another value below it is not sent. With `pumbo.bans.*` true and `pumbo.bans.exempt.*` false only `pumbobans:exempt.*` goes to Pumpkin. The server log names such a wildcard, and `/pp user <name> info` and `permission check` show "not sent to Pumpkin: pumbobans:* hides pumbobans:exempt.*". Below such a wildcard, a permission of another plugin that your data does not name falls back to Pumpkin's own default, so an operator may get it.
- A permission set exactly also wins over a narrower wildcard below it. With `essentials:fly` true and `essentials:fly.*` false, a permission below it that no group or user names gets true from Pumpkin. The server log and `/pp` show "not sent to Pumpkin: essentials:fly hides essentials:fly.*"; give such a permission its own value.
- A permission that Pumpkin, the Pumbo plugins or your data name, without its own decision, below a permission set to true, gets false. A moderator with `pumbo.bans.notify` does not get `pumbobans:notify.silent` from Pumpkin's operator level: give it on its own. With `myplugin:home` for `vip` and `myplugin:home.others` only for `admin`, a vip player gets false for `myplugin:home.others`, on a single server and behind PumboProx alike.

When a player leaves, PumboPerms takes off everything it set (Pumpkin would keep it until the server stops), and when they join again it checks the whole list, so a rank taken away meanwhile is gone. After a change that affects commands, the player gets the command list again, at most once a second; changes in that second go out together.

PumboPerms looks for expired temporary permissions every `provider.refresh-seconds` and each time it runs: a player joins, leaves, changes worlds or sends any command, or another plugin asks PumboPerms. `/tick freeze` stops the periodic check, so during a freeze an expired permission goes at the next of those moments.

One copy of PumboPerms owns `perms.redb` and keeps `perms.redb.lock` fresh every 10 seconds. A second copy on the same folder logs "the database is open in another instance", refuses changes and tries again every 10 seconds. A copy without its database keeps the ranks of the players online, but a player who joins gets only what `default` gives until the database opens. `/tick freeze` stops the periodic refresh: a freeze longer than 30 seconds in which nobody uses a command or joins, together with loading a second copy in that time, lets both copies open the database. A server that crashed or was killed leaves its lock behind, so after a quick restart PumboPerms waits up to 30 seconds: until then it imports nothing, sets no permissions and refuses changes, then opens the database and sets the permissions of the players online.

If PumboPerms crashes (Pumpkin shows the plugin as failed), the permissions it last set stay on online players until the server restarts, temporary ones included. Restart the server; `/plugin unload` does not take them off.

## Limits

Measured on an Apple M4 Pro laptop with release builds of the plugin code; a VPS is often two or three times slower, and the plugin runs as WebAssembly, which adds to that.

|                                             | PumboProx (network)                                                        | Pumpkin (one server)                                     |
| ------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------- |
| Memory                                      | about 45 MB with 300 players online on 10 servers and 3000 more in the database | about 13 MB with 100 players online and 8000 permissions |
| Memory for 400 000 known names              | +0.4 MiB, runs within a 64 MB plugin limit                                 | +0.4 MiB, runs within a 64 MB plugin limit               |
| Start with 400 000 players in a group       | about 1.1 s, within a 64 MB plugin limit                                   | 0.6-1.3 s, 17 MB of plugin memory                        |
| One change among 20 000 players in a group  | heap peak +6.0 MiB (24.4 MiB in 1.0.1)                                     | heap peak +6.0 MiB (24.4 MiB in 1.0.1)                   |
| Change in a group every player has          | about 30 ms for 300 players on 10 servers                                  | about 10 ms for 100 players and 8000 permissions         |
| Change for one player                       | only that player is recomputed                                             | about 4 ms                                               |
| Import of 3000 players                      | `permissions.yml`: 28-44 ms, 14-18 ms again after a change                 | `/pp import <file>`: 27-31 ms, 69-74 ms again (it saves the current data first) |
| Join with 400 000 known names               | up to 0.135 ms (0.57 ms for the first after the start)                     | up to 0.135 ms (0.57 ms for the first after the start)   |
| Opening a database with 400 000 names       | 6 ms                                                                       | 15 ms, with loading the data                             |
| A group with 400 000 members: `info`, `listmembers`, `export` | 6 ms, 0.8 s, 1.3 s                                       | 6 ms, 0.7 s, 1.3 s, no memory beyond the start           |
| Renaming a group with 400 000 members       | over the 200 ms budget from about 200 000 members, see below               | about 4.3 s, 44 MB of plugin memory                      |
| Database after a crash (kill -9)            | opens in 11-17 ms (3000 players)                                           | about 30 s: waits for the old lock to go stale           |

PumboPerms keeps groups, tracks, the players online and the last 64 offline players that a command or another plugin asked about in memory. Every other player stays in `perms.redb` and loads when they join or when something names them, and for each group PumboPerms counts the members on disk, so `group info` reads nothing. The names of all players who joined stay in `perms.redb` too, and memory holds the names of the players online. In a test with 400 000 known names, opening the database and 200 joins with lookups by name and by UUID raised the heap peak by 0.4 MiB; 0.1.2-beta, which kept every name in memory, raised it by 159.3 MiB. A join with 400 000 known names takes up to 0.135 ms, and the first join after the start up to 0.57 ms, while the database cache is empty.

A change keeps a copy of the records it touches, to undo the change if saving fails: one change among 100 000 players in a group raised the heap peak by 0.07 MiB, where 1.0.1 copied all data for 32.5 MiB. The start with 100 000 players in a group took 14.8 MiB of heap (88.1 MiB in 1.0.1), most of it the database cache, and with 400 000 players 14.9 MiB. As WebAssembly, PumboPerms started with 400 000 such players in 17 MB of plugin memory, of which 2 MB is the plugin itself; 1.0.1 did not start with 100 000 of them in 64 MB.

`listmembers`, `rename` and `delete` of a group and `/pp export` read the whole player table. The export writes the players one by one, and the member list keeps only the page you see, so neither grows with the database. A rename rewrites every member in one database transaction: with 100 000 members it needed 25 MB of plugin memory, with 400 000 members 44 MB. Memory still grows with the number of different permission nodes players have, with the number of different end times of temporary groups of offline players, and with the import ledgers, which stay in memory. `/pp import <file>` reads the whole file into memory. `/pp log` reads the log only back to the end of the page you open, also with `log.max-entries: 0`.

On PumboProx (the proxy stops a plugin call after 200 ms of continuous work, `plugins.budget-ms`): a change in a group every player inherits, with 300 players online on 10 servers, 20 groups of 50 permissions and 3000 more players in the database, takes about 30 ms for all 300 new sets, and a change that reaches one player recomputes that player alone. Importing a `permissions.yml` with 3000 players takes 28-44 ms the first time and 14-18 ms again after a change; reading the file, the import and each group of 25 new sets are separate pieces of work for the budget. The import itself is one database transaction, 13-27 ms of that. In a test on PumboProx (built for debugging) with the built `pumbo-perms.wasm`, PumboPerms finished importing a `permissions.yml` with 3000 players in 20 groups of 50 permissions about 120 ms after the proxy started, and a change in `default` reached 200 players online in about 35 ms. No piece of work ran over the budget, also with `plugins.memory-mb: 64`. After a SIGKILL of the proxy, PumboPerms opened its database with 3000 players in 11-17 ms.

A pass over the whole player table (the start, `listmembers`, `rename`, `delete` and `/pp export`) gives the proxy a break every 1024 players. With 400 000 players in one group, the start, `listmembers` and `/pp export` passed even with `plugins.budget-ms: 20`. Renaming a group with about 200 000 members or more runs over the default 200 ms while the database saves the rename, in one piece of work that PumboPerms cannot split. The proxy then stops PumboPerms and starts it again, which takes about a second; the rename does not happen and your data stays as it was. For such a rename, raise `plugins.budget-ms` in `pumboprox.yml`: 500 was enough for 200 000 members, and 1000 for 400 000, where the rename took 4982 ms. A proxy that also stops a plugin after five budgets of work without a wait (at least 5 s) leaves no room there, so use 2000 for 400 000 members: that rename passed in 5106 ms. Deleting a group whose 400 000 members had nothing else took 3.4 s within the default budget; a delete that leaves members with other groups or permissions rewrites them like a rename.

`plugins.memory-mb` in `pumboprox.yml` (256 by default) sets the same limit for each plugin on the proxy, so set it for the plugin that needs the most; 64 MB holds PumboPerms with 400 000 known names. On a test network with `plugins.memory-mb: 64`, a database of 400 000 known names and a `permissions.yml` with 3000 players, PumboPerms opened the database file in 6 ms, imported `permissions.yml` and found `Player399999` in the database for `/pp user Player399999 info`, with no plugin errors in the log. The whole proxy process held 197 744 KB (RSS; 141 312 KB footprint on macOS). With 400 000 players in one group instead of bare names, PumboPerms started within the same 64 MB and with no piece of work over the budget, and the proxy process held 204 096 KB (RSS; 155 648 KB footprint).

PumboProx itself, with 1040 entries per player (20 groups of 50 nodes, entries on 10 servers), answers a permission check in under 7 µs, also when no entry matches. The sets it sends to servers with PumboBridge take 43 ms for 300 players after a change that touches all of them. Reading a player's entries from a `permissions.yml` with 3000 players takes 5 µs at join.

On Pumpkin, PumboPerms handles one call at a time, and Pumpkin waits for it at every player command and join, so while PumboPerms works on a change, commands and joins wait too. A change in a group every player inherits, with 100 players online and 8000 permissions named in the data, takes about 10 ms. A player gets the command list again at most once a second. Set `max_memory_mb = 64` in `[plugins.overrides.pumboperms]`. With that limit and a database of 400 000 known names, PumboPerms on Pumpkin 0.2.0 opened the database and read its data in 15 ms, and `/pp user Player399999 info` showed the UUID from the database, with no plugin errors in the log. With 400 000 players in one group, PumboPerms on Pumpkin 0.2.1 and 0.2.2 read its data in 0.6-1.3 s; `listmembers` of that group took about 0.7 s, `/pp export` 1.3 s and renaming the group 4.3 s, and commands and joins wait that long.
