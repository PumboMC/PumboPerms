# How it works

## How Pumpkin gets the permissions

Pumpkin keeps a list of permission values per player and reads wildcards from the broadest one. It also reads a permission set exactly as a wildcard for everything below it. PumboPerms on Pumpkin and PumboBridge behind PumboProx send each player a list that Pumpkin reads the way PumboPerms decides:

- Every permission of the Pumbo plugins gets its own value (`pumbobans:ban`, `pumbofilter:bypass` and so on), even when your data only has a wildcard such as `pumbo.*`.
- A wildcard with a narrower wildcard of another value below it is not sent. With `pumbo.bans.*` true and `pumbo.bans.exempt.*` false only `pumbobans:exempt.*` goes to Pumpkin. The server log names such a wildcard, and `/pp user <name> info` and `permission check` show "not sent to Pumpkin: pumbobans:* hides pumbobans:exempt.*". Below such a wildcard, a permission of another plugin that your data does not name falls back to Pumpkin's own default, so an operator may get it.
- A permission set exactly also wins over a narrower wildcard below it. With `essentials:fly` true and `essentials:fly.*` false, a permission below it that no group or user names gets true from Pumpkin. The server log and `/pp` show "not sent to Pumpkin: essentials:fly hides essentials:fly.*"; give such a permission its own value.
- A permission that Pumpkin, the Pumbo plugins or your data name, without its own decision, below a permission set to true, gets false. A moderator with `pumbo.bans.notify` does not get `pumbobans:notify.silent` from Pumpkin's operator level: give it on its own. With `myplugin:home` for `vip` and `myplugin:home.others` only for `admin`, a vip player gets false for `myplugin:home.others`, on a single server and behind PumboProx alike.

When a player leaves, PumboPerms takes off everything it set (Pumpkin would keep it until the server stops), and when they join again it checks the whole list, so a rank taken away meanwhile is gone. After a change that affects commands, the player gets the command list again, at most once a second; changes in that second go out together.

PumboPerms looks for expired temporary permissions every `provider.refresh-seconds` and each time it runs: a player joins, leaves, changes worlds or sends any command, or another plugin asks PumboPerms. `/tick freeze` stops the periodic check, so during a freeze an expired permission goes at the next of those moments.

One copy of PumboPerms owns `perms.redb` and keeps `perms.redb.lock` fresh every 10 seconds. A second copy on the same folder logs "the database is open in another instance", refuses changes and tries again every 10 seconds. `/tick freeze` stops the periodic refresh: a freeze longer than 30 seconds in which nobody uses a command or joins, together with loading a second copy in that time, lets both copies open the database. A server that crashed or was killed leaves its lock behind, so after a quick restart PumboPerms waits up to 30 seconds: until then it imports nothing, sets no permissions and refuses changes, then opens the database and sets the permissions of the players online.

If PumboPerms crashes (Pumpkin shows the plugin as failed), the permissions it last set stay on online players until the server restarts, temporary ones included. Restart the server; `/plugin unload` does not take them off.

## Limits

Measured on an Apple M4 Pro laptop with release builds of the plugin code; a VPS is often two or three times slower, and the plugin runs as WebAssembly, which adds to that.

|                                             | PumboProx (network)                                                        | Pumpkin (one server)                                     |
| ------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------- |
| Memory                                      | about 45 MB with 300 players online on 10 servers and 3000 more in the database | about 13 MB with 100 players online and 8000 permissions |
| Memory for 400 000 known names              | +0.4 MiB, runs within a 64 MB plugin limit                                 | +0.4 MiB, runs within a 64 MB plugin limit               |
| One change among 20 000 players in a group  | heap peak +24.4 MiB                                                        | heap peak +24.4 MiB                                      |
| Change in a group every player has          | about 30 ms for 300 players on 10 servers                                  | about 10 ms for 100 players and 8000 permissions         |
| Change for one player                       | only that player is recomputed                                             | about 4 ms                                               |
| Import of 3000 players                      | 28-44 ms, 14-18 ms again after a change                                    | not measured                                             |
| Join with 400 000 known names               | up to 0.135 ms (0.57 ms for the first after the start)                     | up to 0.135 ms (0.57 ms for the first after the start)   |
| Opening a database with 400 000 names       | 6 ms                                                                       | 15 ms, with loading the data                             |
| Database after a crash (kill -9)            | opens in 11-17 ms (3000 players)                                           | about 30 s: waits for the old lock to go stale           |

PumboPerms keeps groups, tracks and players with groups, permissions or meta in memory. The names of all players who joined stay in `perms.redb`, and memory holds the names of the players online. In a test with 400 000 known names, opening the database and 200 joins with lookups by name and by UUID raised the heap peak by 0.4 MiB; 0.1.2-beta, which kept every name in memory, raised it by 159.3 MiB. A join with 400 000 known names takes up to 0.135 ms, and the first join after the start up to 0.57 ms, while the database cache is empty. Loading 20 000 players in one group and making one change raised the heap peak by 24.4 MiB: PumboPerms copies the data at each change, to undo the change if saving fails. `/pp log` reads the log only back to the end of the page you open, also with `log.max-entries: 0`.

On PumboProx (the proxy stops a plugin call after 200 ms of continuous work, `plugins.budget-ms`): a change in a group every player inherits, with 300 players online on 10 servers, 20 groups of 50 permissions and 3000 more players in the database, takes about 30 ms for all 300 new sets, and a change that reaches one player recomputes that player alone. Importing a `permissions.yml` with 3000 players takes 28-44 ms the first time and 14-18 ms again after a change; reading the file, the import and each group of 25 new sets are separate pieces of work for the budget. The import itself is one database transaction, 13-27 ms of that. In a test on PumboProx (built for debugging) with the built `pumbo-perms.wasm`, PumboPerms finished importing a `permissions.yml` with 3000 players in 20 groups of 50 permissions about 120 ms after the proxy started, and a change in `default` reached 200 players online in about 35 ms. No piece of work ran over the budget, also with `plugins.memory-mb: 64`. After a SIGKILL of the proxy, PumboPerms opened its database with 3000 players in 11-17 ms.

`plugins.memory-mb` in `pumboprox.yml` (256 by default) sets the same limit for each plugin on the proxy, so set it for the plugin that needs the most; 64 MB holds PumboPerms with 400 000 known names. On a test network with `plugins.memory-mb: 64`, a database of 400 000 known names and a `permissions.yml` with 3000 players, PumboPerms opened the database file in 6 ms, imported `permissions.yml` and found `Player399999` in the database for `/pp user Player399999 info`, with no plugin errors in the log. The whole proxy process held 197 744 KB (RSS; 141 312 KB footprint on macOS).

PumboProx itself, with 1040 entries per player (20 groups of 50 nodes, entries on 10 servers), answers a permission check in under 7 µs, also when no entry matches. The sets it sends to servers with PumboBridge take 43 ms for 300 players after a change that touches all of them. Reading a player's entries from a `permissions.yml` with 3000 players takes 5 µs at join.

On Pumpkin, PumboPerms handles one call at a time, and Pumpkin waits for it at every player command and join, so while PumboPerms works on a change, commands and joins wait too. A change in a group every player inherits, with 100 players online and 8000 permissions named in the data, takes about 10 ms. A player gets the command list again at most once a second. Set `max_memory_mb = 64` in `[plugins.overrides.pumboperms]`. With that limit and a database of 400 000 known names, PumboPerms on Pumpkin 0.2.0 opened the database and read its data in 15 ms, and `/pp user Player399999 info` showed the UUID from the database, with no plugin errors in the log.
